None of the new records overlaps an existing record or another new one (same title and overlapping bursts). The 87 human records are unchanged.
- **Changed fixtures.** Four serving-mode fixtures changed: `short_lake_build` in `tests/jobs/test_retrain.py`, plus the e2e lake and `synthetic_lake` in `tests/ml/test_cutoff.py`. Each now links its pages from the portal so that every day counts as labeled. No assertion was changed or removed. The assertions in those tests check features, splits and day lists, not label values. `match="final portal"` in `test_the_test_split_is_the_newest_final_days...` still matches the reworded message.
- **Scope.** The labeler prompt and model are unchanged: `wikipulse/eval/label.py` isn't in the diff, and `ML_RETRAIN_LABEL_MODEL` defaults to the existing qwen3:4b. The order is by day, not by uncertainty, so this isn't active learning. Nothing under `data/` and no `.env` is committed. No email address appears in the diff. All LLM calls go through `wikipulse.llm.get_client`.
- **Event time.** `find_rows(..., now)` uses `now` only to reject a future `--as-of`. `datetime.now` is used only for `labeled_at` metadata and `built_at`. `deadline()` uses `time.monotonic()` as a cost limit, not as processing logic. Readiness, splits and purges all use `as_of`, which is the lake's end or an explicit moment. The splits are still purged by `purge_boundaries` and stay in time order: delayed days are left out, never put into training.
- **Failure handling.** `StructuredOutputError` (both `LLMError` and `ValueError`) is caught by the `ValueError` branch first, so it skips one spike. The Ollama backend turns timeouts and connection errors into `LLMUnavailableError`, which ends the run cleanly. `httpx.HTTPError` from Wikimedia stops further requests.

## Problems

1. **medium**, `wikipulse/config.py:471`: the default `ML_RETRAIN_LABEL_BUDGET=150` is well below the weekly need shown by this branch's own numbers. On 10 Nov, 56 of 87 spikes were unlabeled, which is roughly 350 to 450 new unlabeled spikes a week. The 40-minute limit would allow about 650 calls at the ~3.5 s/spike seen in the run. The budget therefore covers the test days (labeled newest first) every week, but the validation and training days fall further behind week after week, and nothing documents or reports this backlog over time.
2. **low**, `wikipulse/ml/fresh_labels.py:60` vs `wikipulse/ml/dataset.py:445`: `needs_label` treats a spike as judged when any record covers it, while `is_labeled` also requires `label.end_at < as_of`. A spike covered only by a record whose burst ends at or after `as_of` (for example a longer burst from another run) is never sent to the labeler, but it still counts as unlabeled for readiness, so it can hold its day back for good.
3. **low**, `wikipulse/ml/dataset.py:445`: `unsure` counts as labeled for readiness, but evaluation treats it as unknown. A day full of `unsure` answers is "ready" yet adds no comparable test rows, so requirement 3 ("too few labeled rows only when the delayed split is too small") is weaker than it sounds. The choice is documented, but the rejection message doesn't separate `unsure` from unlabeled rows.
4. **low**, `docker-compose.yml:148`: `OLLAMA_HOST=http://host.docker.internal:11434` works on Docker Desktop, but the Airflow service has no `extra_hosts: ["host.docker.internal:host-gateway"]`. On a plain Linux Docker Engine the task would quietly log "labeler unavailable" every week and add no labels. CI doesn't run this profile, so nothing breaks today.
5. **low**, `wikipulse/jobs/retrain.py:283`: the Wikipedia cache directory `settings.data_dir / "cache" / "wikipedia"` is copied from `wikipulse/eval/label.py:345` instead of coming from one place (config or a shared helper).
6. **low**, `wikipulse/ml/dataset.py:1028-1031`: after the `find_rows` extraction, `build()` unpacks `FoundRows` into about 15 locals through chained tuple assignments. That's a mechanical refactor that is harder to read than using `found.x` directly.
7. **low**, `wikipulse/jobs/retrain.py:111`: `too_few_rows` reports `delayed_rows` as "rows", but the count is selected spikes before `purge_boundaries`, so it isn't on the same basis as the labeled and unlabeled row counts in the same message.
8. **low**, `wikipulse/ml/fresh_labels.py` (design): the weekly DAG appends to the git-tracked `evals/labels/spike_labels.jsonl` through the bind mount. After every run the working tree is dirty, and later dataset manifests record a "dirty" commit. The branch doesn't document who commits these labels or when; this branch did it by hand in de2876f.
9. **low**, `wikipulse/lake/lock.py:71-79` (outside this spec): "Lost the lake writer lock" is logged at ERROR by `renew()` even when `Backfill.keep_lock()` takes the lock straight back after its TTL expired during a reconnect. That is the intended recovery path, not a bug in `backfill.py`, but the log level is misleading. The learning note mentions it, but it isn't recorded as a ROADMAP follow-up.

Verdict: merge

## Questions for the human before merging

1. With the default budget of 150 and roughly 60 new spikes a day, which splits of next month's datasets will have LLM labels and which will slowly fill with unknown rows? Would you raise `ML_RETRAIN_LABEL_BUDGET`, or accept that only the test and validation days get fresh labels?
2. The acceptance run used `as_of = 15 Nov 18:00` on a lake that ends on 11 Nov. In the normal weekly run `as_of` is empty. Which days will be test days then, which will be delayed, and why does the labeling task still label the delayed days?
3. The labeling task counts any existing record, including an `unsure` or a qwen3:8b label, as "judged" and never asks again. If you later fix the labeler's prompt (the 12b over-calls-news follow-up), how would the new labels get into the datasets, and what would this task do on its own?
