## Problems

1. **medium**, `wikipulse/qa/cypher.py:71, 112-121`: `_FINAL_LIMIT` is matched against the raw query, not the blanked skeleton. As a result, `MATCH (n) RETURN n.name // LIMIT 1000` comes out as `... // LIMIT 25`, with the limit inside the comment and none on the query. Also, in a `UNION` query only the last branch is limited. The module docstring's claim that "the final result always gets its own" LIMIT is therefore false, and only the client-side row cap and the timeout bound the server's work.
2. **medium**, `wikipulse/qa/cypher.py:70, 91-109`: `_check_hops` only looks inside `[...]`, and `_QUANTIFIER` only catches `)+`, `)*` and `){m,n}`. So quantified relationships such as `(a)-[:RELATED_TO]-+(b)`, `-[:RELATED_TO]-{1,}` and `SHORTEST 1 (a)-[:R]-+(b)` pass validation, and Neo4j 5.26 accepts them (I checked with `EXPLAIN`). These are unbounded traversals, and only the 5 s timeout stops them.
3. **medium**, `wikipulse/qa/answer.py:111, 183-192`: `claims()` ignores any piece with fewer than 3 words, so `uncited_sentences("Peña resigned. Bank failed [F1].")` and an uncited list item like `- Ueno Bank` both return `[]`. Sentences still uncited after the retry stay in `Answer.text` with only a warning. Requirement 3 is therefore enforced only partly.
4. **medium**, `wikipulse/qa/retrieve.py:482-485` / `wikipulse/qa/ask.py:343-344`: when the generated query hits `QA_CYPHER_MAX_ROWS`, the "there may be more" note reaches the model only as a search note, and `render` shows notes only with `--show-context`. The Q4 answer presented 22 of 29 organizations as the complete list without telling the user, and Q1 and Q2 also present partial lists as complete.
5. **low**, `wikipulse/qa/cypher.py:30` vs `prompts/cypher_v1.md:38` vs `retrieve.py:95`: three hop limits disagree. The validator allows 6 hops, the prompt says at most 4, and traversal uses 4.
6. **low**, `wikipulse/qa/cypher.py:34-56`: the forbidden-word check does not consider where a word appears. Harmless read queries are rejected, for example `RETURN n.type AS set`, `RETURN n.name AS start` and `RETURN (1+2)*3` (which is reported as a "quantified path pattern").
7. **low**, `wikipulse/qa/retrieve.py:87-100`: `RetrievalConfig` repeats the five defaults from `config.py` (25, 5.0, 5, 0.63, 60), so there are two sources of truth. It also hard-codes eight other retrieval tunables (`max_hops`, `max_entities`, `max_seed_events`, `period_events`, ...) that are not in `config.py`.
8. **low**, `wikipulse/qa/retrieve.py:519-529`: `_assemble` calls `event_entities`/`event_relations` outside `_timed`, so a Neo4j error there raises instead of becoming a note, unlike the module docstring's promise that "a failing channel leaves a note".
9. **low**, `wikipulse/qa/retrieve.py:57`: `_EVENT_KEY` (`^[\w.-]+:\d+$`) also matches values like `"10:30"` or `"3:2"`. A query column holding such values would be hidden from the fact text by `_only_event_keys` and looked up as an event.
10. **low**, `wikipulse/qa/retrieve.py:158-166`: an event fact cites the event's two highest-scoring pages, whether or not those pages support the event's LLM-written description. In Q3, the claim that "Ueno Bank's collapse ... led to Santiago Peña's resignation" cites *Pedro Alliana*.
11. **low**, `wikipulse/qa/graph.py:138-139`: `plain_value(Path)` keeps only the nodes, so `source_title`/`source_revision` on the relationships of a path returned by a generated query are lost, and `row_sources` cannot cite them.
12. **low**, `wikipulse/qa/index.py:52-62, 109-123`: `embedding_model` is stored but never compared with the query embedder's model. Also, `CREATE VECTOR INDEX ... IF NOT EXISTS` keeps the old dimension if `EVENTS_EMBED_MODEL` changes. A changed model would silently compare vectors from different embedding spaces.
13. **low**, `tests/qa/test_qa_neo4j.py:147, 185-219`: the integration tests write 2031-dated events into the shared development graph rather than a separate test database. Teardown cleans up, but if a run is killed between write and teardown, `QAGraph.clock()` and every "today" answer jump to 2031.

Verdict: fix

The safety design is sound where it matters. Neo4j's READ access mode, the transaction timeout and the row cap all hold, and I confirmed each one. The four acceptance answers that should answer are correct and cited, and the refusal works. Problems 1–4 are small, local fixes: limit the skeleton and refuse `UNION`, catch `]-+` and `]-{m,}`, check short claims, and show the truncation note. They should be fixed before 05b measures this pipeline.

## Questions for the human before merging

1. `validate_cypher` rejects writes, but Neo4j also refuses them because `run_query` uses a READ session. If you deleted `validate_cypher` entirely, what could a bad generated query still do to the system, and which of the remaining safeguards (timeout, row cap, limit) would stop it?
2. For "What happened today?", the generated Cypher, the `time_window` listing and vector search can all find the same events. Why does `_listed_by_query()` drop the period-listed events here, and what would the model see if the generated query returned 0 rows, as it did in the author's first run?
3. An event fact cites the event's top two `PART_OF` pages, while a relation fact cites the exact revision it was extracted from. Which kind of citation should you trust more when checking a claim like "the bank's collapse led to the resignation", and why?
